## Решение по блокам

### A — базовый

Чтение данных, осмотр типов и доли отмен, разделение на `train / validation / test` **до любого fit**, логистическая регрессия, интерпретация confusion matrix: **FP = клиент не отменил, но модель сочла бронь отменённой** (опасность овербукинга).

### B — основной

Проверка пропусков, дублей, ошибок и выбросов. Только разрешённые признаки на момент бронирования. `ColumnTransformer` с медианой и StandardScaler для чисел, отдельной категорией для пропущенного текста и OneHotEncoder для категорий. `StratifiedKFold(5)` на данных без повторяющихся признаков; если найдены идентичные записи, автоматически применяется `StratifiedGroupKFold(5)` — чтобы копии бронирований не попадали между фолдами. Сравнение логистической регрессии с деревом. Порог под бизнес-задачу выбирается на **validation**, не на test. **Тест используется только в конце.**

### C — продвинутый

- Утечки: `reservation_status` и `reservation_status_date` прямо отражают исход; `assigned_room_type`, `booking_changes`, `days_in_waiting_list`, `total_of_special_requests` могут меняться после создания брони. Исключены. `company` (почти пусто), `agent` (идентификатор), `adr` (может меняться), `required_car_parking_spaces` и дублирующий признак недели исключены как неочевидные или лишние в консервативной модели.
- Два способа борьбы с дисбалансом **внутри CV**: `class_weight="balanced"` и `RandomOverSampler` внутри `imblearn.Pipeline`; сравнение с неотбалансированным вариантом. Выбор по CV PR-AUC.
- Групповой анализ ошибок: `hotel`, `market_segment`, `deposit_type` — FP, FN, false positive rate, false negative rate и precision.
- Ограничения: временной дрейф, возможное совпадение одинаковых бронирований в train/test, неясный момент фиксации признаков, несогласованные цены ошибок, отсутствие калибровки вероятностей.

## Почему высокая precision важнее просто accuracy

Если модель говорит «отменит», но гость **приезжает**, отель рискует перепродать номер, выплатить компенсацию и потерять репутацию. Поэтому сравниваем precision, а не только accuracy. Для наглядности показана цель **precision ≥ 0.95** на validation с ограничением по количеству предсказаний. **Это учебный порог, заказчик его не утверждал.** Если достигнуть нельзя, вывод: **не использовать модель для автоматического овербукинга**.

## Проверки

```bash
python3 -m unittest discover -s tests -v
```

Отчёты после запуска находятся в `results/demo/` или `results/full/`: `cross_validation.csv`, `missing.csv`, `audit.csv`, `thresholds_validation.csv`, `group_errors_test.csv`, `summary.json` и графики.

**Что сказать на защите:**

1. **Почему нельзя оставлять `reservation_status`?** Оно формируется после исхода и выдаёт ответ; на момент первоначальной брони его не существует.
2. **Почему oversampling внутри pipeline?** Иначе копии объектов редкого класса попадут в fold валидации — утечка и завышение метрик.
3. **Зачем тест отдельно от выбора порога?** Подбор порога на test подгоняет решение под ответы теста и делает проверку необъективной.
4. **Какая ошибка дороже?** FP: предсказали отмену, но гость приехал; FN означает, что модель не обнаружила будущую отмену.
5. **Готова ли модель к овербукингу?** Нет, пока не подтверждены показатели на реальном свежем датасете, бизнес-стоимость ошибок и безопасность принятия решения.
